2. Mục tiêu thực hành

Triển khai ứng dụng Hello Cloud API bằng Node.js và Express trên GitHub Codespaces. Quan sát tài nguyên đám mây và đối chiếu với 5 đặc tính điện toán đám mây của NIST.

4. Năm đặc tính điện toán đám mây NIST

  1. On-demand self-service: Sinh viên tự tạo Codespace trên GitHub mà không cần nhân viên quản trị cấp máy.
  2. Broad network access: API có thể được truy cập bằng trình duyệt trên laptop và điện thoại qua Internet.
  3. Resource pooling: GitHub cung cấp môi trường tính toán từ hạ tầng tài nguyên dùng chung, sinh viên không phải chọn máy chủ vật lý cụ thể.
  4. Rapid elasticity: Dịch vụ đám mây cho phép điều chỉnh tài nguyên linh hoạt theo nhu cầu. Bài thực hành mới minh họa bước cấp phát nhanh, chưa kiểm chứng trực tiếp khả năng tự co giãn.
  5. Measured service: Mức sử dụng Codespaces được theo dõi qua Billing Usage, gồm tài nguyên tính toán và lưu trữ.

5. Kết quả thực hành

Đã xây dựng Hello Cloud API để hiển thị hostname, hệ điều hành, CPU, RAM, uptime và thời gian của môi trường chạy.

Đã kiểm tra truy cập từ điện thoại và chuyển cổng về Private sau khi thử nghiệm.

Thời gian cấp phát Codespace: Điền số giây/phút đo được.

6. Kết luận

GitHub Codespaces giúp chuẩn bị môi trường lập trình từ xa, giảm nhu cầu cài đặt trực tiếp trên máy cá nhân và hỗ trợ truy cập ứng dụng qua Internet.

BÀI 2: ẢO HÓA, CONTAINER VÀ CLOUDSIM PLUS

Sinh viên: Trương Thành Lắm

1. Mục tiêu thực hành

Đóng gói ứng dụng Hello Cloud API bằng Docker, chạy nhiều container với giới hạn CPU và RAM, đưa Docker image lên GitHub Container Registry, đồng thời mô phỏng việc phân bổ máy ảo và lập lịch tác vụ bằng CloudSim Plus.

2. Kết quả thực hành Docker

GitHub Container Registry: Xem Docker image trên GHCR

Container notes1 sử dụng cổng 3000. Container notes2 sử dụng cổng 3001, giới hạn CPU 0.5 và RAM 128 MiB.

Lưu ý: Hạn mức GB-tháng không phải kích thước thực tế của máy ảo. Codespaces cung cấp môi trường phát triển container trên hạ tầng do GitHub quản lý.

4. Kết quả mô phỏng CloudSim Plus

Các kết quả cần được đối chiếu với cấu hình Java của từng lần chạy. Nếu Cloudlet không hoàn thành do thiếu tài nguyên, cần ghi nhận và giải thích thay vì bỏ qua.

5. Nhận xét kết quả

Việc tăng số VM có thể làm thay đổi kết quả mô phỏng, nhưng hiệu quả phụ thuộc vào khả năng cấp phát tài nguyên của Host.

Khi tăng số Cloudlet mà không tăng tài nguyên, các tác vụ có thể phải chia sẻ CPU hoặc chờ, dẫn đến thời gian hoàn thành thay đổi.

Time-Shared cho phép các tác vụ chia sẻ thời gian CPU. Space-Shared cấp lõi cho các tác vụ phù hợp, còn tác vụ chưa đủ tài nguyên phải chờ.

Lần 1: Nhân đôi số máy ảo

Lần 2: Nhân đôi số Cloudlet

Lần 3: Space-Shared Scheduler

7. Câu hỏi phản biện

Câu 1: Vì sao notes2 có thể báo RAM bằng host dù đã giới hạn 128 MiB?

Vì API os.totalmem() có thể đọc dung lượng RAM của hệ điều hành host thay vì giới hạn cgroups. Docker áp dụng giới hạn 128 MiB cho container. Ứng dụng Node.js hoặc Java cần kiểm tra tài nguyên thực tế, tránh sử dụng vượt giới hạn gây OOMKilled.

Câu 2: Time-Shared và Space-Shared khác nhau thế nào?

Time-Shared chia sẻ thời gian CPU giữa các tác vụ, giúp nhiều tác vụ tiến triển đồng thời. Space-Shared cấp tài nguyên cho một số tác vụ, còn các tác vụ khác phải chờ khi thiếu lõi CPU.

Nhà cung cấp dịch vụ giá rẻ có thể ưu tiên chia sẻ tài nguyên để tăng mức sử dụng, nhưng cần cân nhắc hiệu năng và chất lượng dịch vụ cam kết.

Câu 3: Mô phỏng có ích gì trước khi thuê hạ tầng thật?

Mô phỏng giúp đánh giá việc phân bổ VM, số lượng tác vụ và chính sách lập lịch mà không cần thuê máy chủ thực tế. Tuy nhiên, kết quả có thể sai lệch do độ trễ mạng, hiệu năng ổ đĩa, tải hệ thống và lỗi phần cứng chưa được mô phỏng đầy đủ.

8. Kết luận Bài 2

Qua bài thực hành, sinh viên đã tìm hiểu cách đóng gói và triển khai ứng dụng bằng Docker, giới hạn tài nguyên container, xuất bản image trên GHCR và nghiên cứu mô phỏng phân bổ tài nguyên bằng CloudSim Plus.

BÀI 3: LƯU TRỮ PHÂN TÁN

1. Kết quả thực hành

Đã kết nối Notes API với MongoDB Atlas và Supabase Storage, thực hiện CRUD, tải tệp và lưu URL đính kèm.

2. Hiệu quả chỉ mục MongoDB

Chỉ mục giúp giảm 71,45% số tài liệu cần đọc. Thời gian của cả hai truy vấn là 1 ms nên chưa quan sát được khác biệt rõ ràng về thời gian.

3. Câu hỏi phản biện

Câu 1: Khi dữ liệu tăng lên 2 triệu?

Nếu giữ nguyên tỷ lệ chọn lọc của thí nghiệm, quét toàn bộ có thể cần kiểm tra khoảng 2 triệu tài liệu, trong khi dùng chỉ mục khoảng 571 nghìn tài liệu. Đây chỉ là ước lượng, không phải số đo. Với giới hạn 100 thao tác/giây của tình huống đề bài, truy vấn kém hiệu quả có thể làm tăng tải hệ thống và độ trễ.

Câu 2: Vì sao dùng Supabase Storage?

Supabase Storage phù hợp để lưu tệp đính kèm và cung cấp đường dẫn truy cập. MongoDB chỉ cần lưu URL và thông tin ghi chú, giúp tài liệu gọn hơn, tránh phải lưu nội dung tệp trực tiếp trong tài liệu NoSQL.

Câu 3: Atlas khác HDFS thế nào?

Cả hai dùng nhân bản để tăng khả năng chịu lỗi và tính sẵn sàng của dữ liệu. MongoDB Atlas nhân bản dữ liệu giữa các nút Primary và Secondary. HDFS nhân bản các block của tệp trên nhiều DataNode; NameNode quản lý metadata. Số 3 giúp cân bằng khả năng chịu lỗi và chi phí lưu trữ.
